# transcription-benchmarking

This repository runs singing transcription systems on identical recordings and scores their output with a common
procedure. It reports results for fifteen published systems and transcPybe on the three annotated datasets that none
of them was trained on, with full results on five datasets in [RESULTS.md](RESULTS.md). It also describes how the
results were obtained, and explains how to apply the benchmark to other data and systems.

## The benchmark

### System selection

A systematic survey ([`docs/vocal-transcription-tools.md`](docs/vocal-transcription-tools.md)) identified 48 candidate
systems. Of these, 25 were runnable, produced note-level output and were applicable to singing. Ten of the 25 were
not run:

- five are other versions of a system that was run;
- two have weights that are not publicly available;
- two do not produce timed notes;
- one was not trained on singing.

The survey's [What was run](docs/vocal-transcription-tools.md#what-was-run) table lists each of these systems with the
reason. The remaining fifteen were evaluated.

### Procedure

- **Containers.** Each system was run in its own container (`orchestrator/`), built from the authors' code at a fixed
  commit, with their published weights and with network access disabled.
- **Settings.** Published systems were run with their authors' default settings, and no parameters were tuned on these
  datasets. Where a system required a modification in order to run, the modification is recorded in its image
  definition (`orchestrator/images/`).
- **Scoring.** All systems received identical audio and produced MIDI output, and each recording was scored with this
  package's metrics.

## Usage

### Scoring a system's output

```shell
pip install -e .
transcription-benchmark AUDIO_DIR --annotations ANNOTATION_DIR --estimates OUTPUT_DIR -o results/system.json
```

`OUTPUT_DIR` contains one MIDI or CSV file per recording, matched to the audio by file name. The report gives COn, COnP
and COnPOff with 95% intervals from a bootstrap over recordings.

Two checks are recommended before scoring:

- `--inspect DATASET` shows how the annotations were interpreted: whether a column holds offsets or durations, and
  whether pitch is given in MIDI note numbers or in hertz.
- `--dry-run` shows which annotation was paired with each recording, without reading any audio.

### Comparing two systems

```shell
transcription-benchmark --compare a.json b.json
```

This estimates the paired difference between two runs by bootstrapping over the recordings they share. Overlapping
confidence intervals do not establish that two systems perform equally; the paired comparison addresses that question
directly. `--by-metadata FILE:COLUMN` reports the comparison separately for each value of a column in a metadata CSV,
such as language.

### Running all systems on a dataset

```shell
cd orchestrator
./bench.py all --audio AUDIO_DIR -a ANNOTATION_DIR
```

This builds each system's image, transcribes the audio, and scores and compares the results. `--only game,basic-pitch`
restricts the run to the named systems. [`orchestrator/README.md`](orchestrator/README.md) describes the setup:

- Docker and the NVIDIA Container Toolkit;
- about 35 GB of images;
- the checkpoints that must be downloaded manually.

### Adding a system

A system that writes MIDI or CSV files requires no code: run it, then pass its output directory to `--estimates`. For
the benchmark to call a system directly, with results cached on its settings, the system's package registers an
adapter:

```toml
[project.entry-points."transcription_benchmarking.transcribers"]
mysystem = "mypackage.adapter:MySystem"
```

```python
class MySystem:
    def transcribe(self, audio: Path) -> Sequence[tuple[float, float, float]]:
        """(onset in seconds, offset in seconds, MIDI pitch) for each note."""

    def settings(self) -> dict:
        """Optional: recorded with the result, and used as the cache key."""
```

`--list-transcribers` lists the installed adapters, and `--transcriber NAME` runs one.

### Dataset options

| Option | Purpose |
|---|---|
| `--annotations-json FILE` | A single JSON file for the whole corpus, keyed by recording, as M4Singer and MIR-ST500 are distributed. |
| `--pairs FILE` | An explicit CSV pairing audio files with annotations, where file names do not correspond. |
| `--annotation-contains TEXT` | Selection among several annotations of one recording. |
| `--items FILE` | Restriction to a published split. |
| `--sample N` | N recordings drawn from across the corpus, rather than the first N. |
| `--align` | References notated at a nominal tempo: each is aligned to its recording's pitch contour. |
| `--onset-shift SECONDS` | References that place note onsets at a different point, such as the consonant. Only estimated onsets are moved. |
| `--time-offset SECONDS` | References offset from their audio by a constant. |

The last three options correct for properties of the references. Each correction is recorded in the result and stated
in the report. None was applied in the results above.

### Inter-annotator agreement

```shell
transcription-benchmark vocadito/annotations --agreement notesA1 notesA2 -o ceiling.json
```

This scores one annotator's notes against another's. On vocadito, the two annotators agree at COn 0.817, COnP 0.740
and COnPOff 0.642. The last figure matches the 0.64 reported in the vocadito paper.

## Reproducibility

Every result records:

- the system and its settings;
- the random seed;
- the versions of the relevant packages;
- this repository's commit;
- a SHA-256 digest of the dataset files.

`python scripts/readme_results.py` regenerates the results above and [RESULTS.md](RESULTS.md) from two files:
`scripts/scores.json`, which holds every row's COnPOff@50 for each recording, and `scripts/timing.jsonl`. A test fails
if either file and these disagree. `python scripts/results_table.py --tests` reports the paired tests between adjacent
systems in the full table's ranking.

`--cache-dir` reuses transcriptions, keyed on the system's settings. If a system's parameters are tuned on a dataset,
its score on that dataset no longer estimates performance on unseen recordings. Results should then be reported on
another dataset or on a held-out split.
